### Fixed
- **Non-retryable evaluator errors no longer masquerade as agent failures with `metrics: 0`** ([services/evaluation/evaluatorError.ts](services/evaluation/evaluatorError.ts) (new), [services/traces/tracePoller.ts](services/traces/tracePoller.ts), [services/traces/browserRecovery.ts](services/traces/browserRecovery.ts), [services/evaluationRunner.ts](services/evaluationRunner.ts), [services/benchmarkRunner.ts](services/benchmarkRunner.ts), [components/RunDetailsContent.tsx](components/RunDetailsContent.tsx), [components/evals3/ResultStatus.tsx](components/evals3/ResultStatus.tsx), [server/services/storage/statsComputation.ts](server/services/storage/statsComputation.ts), [server/services/storage/index.ts](server/services/storage/index.ts), [server/services/benchmarkRunStats.ts](server/services/benchmarkRunStats.ts), [server/routes/storage/benchmarks.ts](server/routes/storage/benchmarks.ts), [services/storage/opensearchClient.ts](services/storage/opensearchClient.ts), [lib/runStats.ts](lib/runStats.ts), [types/index.ts](types/index.ts), [cli/commands/benchmark.ts](cli/commands/benchmark.ts), [components/evals3/BenchmarkRunsPage.tsx](components/evals3/BenchmarkRunsPage.tsx), [components/evals3/BenchmarksPage.tsx](components/evals3/BenchmarksPage.tsx), [components/evals3/EvalRunDetailPage.tsx](components/evals3/EvalRunDetailPage.tsx), [components/BenchmarkRunsPage.tsx](components/BenchmarkRunsPage.tsx), [components/RunDetailsPage.tsx](components/RunDetailsPage.tsx)): when a trace-mode run finished but the LLM judge then threw a non-retryable validation error (e.g. `Bedrock Judge validation error (not retryable): Missing required field: expectedOutcomes or expectedTrajectory`), the evaluator failure was silently degraded into a normal `completed` run with `metrics: { all 0 }`, `passFailStatus: 'failed'`, and the surface field `llmJudgeReasoning` left at its `'Waiting for traces to become available...'` placeholder. The actual cause was hidden in a separate `traceError` field that nothing surfaced in the Judge tab or in benchmark summaries, and the run was bucketed as a regular `failed` test — indistinguishable from a real agent miss. Aggregate pass rates absorbed the false zero, hill-climbing signals were poisoned, and debugging pointed users at trace propagation when the real problem was a misconfigured evaluator. [#242](https://github.com/opensearch-project/agent-health/issues/242).
  - **New shared helper `buildEvaluatorErrorPatch(kind, error)`** ([services/evaluation/evaluatorError.ts](services/evaluation/evaluatorError.ts)) returns the canonical patch every error site must persist: `metricsStatus: 'error'`, a machine-readable `traceError` prefixed by the failure kind (`Judge evaluation failed`, `Traces never arrived`, `Trace did not converge`, `Post-trace callback failed`, `Trace fetch failed`, `Evaluator error`), an explicit human-readable `llmJudgeReasoning` ("**Evaluator could not run.** ... **Reason (kind):** <message>") that overwrites the misleading `'Waiting for traces...'` placeholder, `passFailStatus: undefined` so the run can't be silently bucketed as passed/failed, and zeroed `metrics`. Six call sites now share this helper: the four error paths in `tracePoller.ts` (incomplete trace, callback failure, max-attempts timeout, fetch error), the post-trace judge-failure paths in `evaluationRunner.ts` and `benchmarkRunner.ts` (both the storage-module and raw-client variants), the browser-side recovery in `browserRecovery.ts`, and the inline judge-retry in `RunDetailsContent.tsx`.
  - **`RunStats` gains an `errored` bucket** ([types/index.ts](types/index.ts), [services/storage/opensearchClient.ts](services/storage/opensearchClient.ts), [lib/runStats.ts](lib/runStats.ts)): the previous shape `{ passed, failed, pending, total }` lumped evaluator failures into `failed`; the new shape `{ passed, failed, pending, errored, total }` separates them so a misconfigured judge run isn't counted toward the agent's failure rate. Optional for backward-compat — older stored runs read as `errored: 0`.
  - **Pass-rate denominator excludes errored runs.** All four stats-computation sites (`server/services/storage/statsComputation.ts`, `server/services/storage/index.ts`, `server/services/benchmarkRunStats.ts`, `server/routes/storage/benchmarks.ts`) now check `report.metricsStatus === 'error'` before falling through to the `passFailStatus` branch and increment `errored++` instead. The shared `lib/runStats.ts` (used by both UI and CLI) computes `passRate = passed / max(0, total - errored)`, so a benchmark whose judge couldn't run on 1/3 cases reports 0/2 (0%) or 2/2 (100%) instead of 0/3 (0%). The runner-level inline stats refresh in `services/benchmarkRunner.ts` follows the same pattern.
  - **`ResultStatus` gains `'errored'`** ([components/evals3/ResultStatus.tsx](components/evals3/ResultStatus.tsx)): `getResultStatus` previously mapped `report.metricsStatus === 'error'` to `'failed'`; it now returns `'errored'`, surfaced in the UI with an amber `AlertTriangle` icon and the badge text `ERRORED`. The status description reads `Evaluator could not run`. All callers (`RunInspectorPage`, `BenchmarkRunDetailPage`, `RunDetailsPage`, `RunDetailsContent`) inherit the new state without code changes — they switch on the type and the new variant lights up automatically.
  - **UI shows the errored count next to passed/failed.** The Benchmark runs list (`components/evals3/BenchmarkRunsPage.tsx` and the legacy `components/BenchmarkRunsPage.tsx`), the run-detail header (`components/RunDetailsPage.tsx`), and the eval-run detail card (`components/evals3/EvalRunDetailPage.tsx`) render an amber `⚠ N` badge when `stats.errored > 0`, with a tooltip explaining "Evaluator could not run (e.g. judge validation error). Excluded from pass-rate aggregation.". The eval-run detail card also adds a footnote explaining the pass-rate denominator excludes errored cases. The legacy `BenchmarksPage` `computeScore` helper uses the same `total - errored` denominator so leaderboard-style scores aren't dragged to 0 by evaluator misconfiguration.
  - **CLI summary calls out errored runs.** `cli/commands/benchmark.ts` appends `(N errored — evaluator could not run)` to the spinner output when `stats.errored > 0`, so users running `agent-health benchmark -f file.json -a my-agent` immediately see the difference between "agent answered terribly" and "the judge never produced a verdict".
  - **Tests.** New [tests/unit/services/evaluation/evaluatorError.test.ts](tests/unit/services/evaluation/evaluatorError.test.ts) covers `buildEvaluatorErrorPatch` end-to-end: the metrics-zeroed contract, `passFailStatus` always undefined, `llmJudgeReasoning` never matches `/waiting for traces/i` and always contains the underlying error message and the `(kind)` tag, the per-kind `traceError` prefixes, non-Error inputs (string and object) handled without `[object Object]` leakage, and the markdown-formatted self-contained surface message that the Judge tab renders. The shared stats-computation test suite ([tests/unit/server/services/storage/statsComputation.test.ts](tests/unit/server/services/storage/statsComputation.test.ts)) adds two regression cases against the bug from the issue: (a) `metricsStatus='error'` is bucketed as errored not failed even when mixed with genuine passes/fails, and (b) `metricsStatus` wins over `passFailStatus` when defensive code somewhere left `passFailStatus: 'passed'` on a stale errored report. All existing stats tests across `tests/unit/server/services/{benchmarkRunStats,storage/statsComputation}.test.ts` and `tests/unit/server/routes/storage/benchmarks-stats.test.ts` were extended to assert `errored: 0` on the round-trip stats objects so the schema change is covered everywhere it's checked.

### Changed
- **Env vars renamed `AGENT_HEALTH_*` → `AH_*`**: All seven user-facing env vars now use the shorter `AH_` prefix (`AH_PORT`, `AH_DEV_PORT`, `AH_API_KEY`, `AH_HEADLESS`, `AH_USERNAME`, `AH_DISABLE_CODING_ANALYTICS`, `AH_SUPPRESS_EXPERIMENTAL`). Legacy `AGENT_HEALTH_*` names are still accepted for backward compatibility and emit a one-time deprecation warning per process; set `AH_QUIET_DEPRECATIONS=1` to suppress. Old names will be removed in a future release. OpenTelemetry span attribute constants (`agent_health.*`) are unchanged. Existing `.env` files, CI configs, and Docker compose files keep working.
- **Public SDK is now compiled per-file (`tsc`) instead of bundled (`esbuild`), so consumers can debug agent-health from inside `node_modules/`** ([package.json](package.json), [tsconfig.lib.json](tsconfig.lib.json) (new), [examples/](examples/) (new)): the `build:lib` step previously ran `esbuild lib/index.ts lib/config/index.ts --bundle --outdir=lib/dist`, which collapsed the public API surface and every transitively-imported file into two ~2400-line bundles (`lib/dist/index.js`, `lib/dist/config/index.js`) with **no `.d.ts`, no sourcemaps, and most JSDoc stripped**. When something didn't behave the way a user expected — `BaseConnector` lifecycle, `JudgeContext` shape, why a matcher reported what it did — the user's AI assistant had two bad options: grep through a 2.4k-line bundled blob with no types, or look at GitHub `main` (which is almost certainly a different version than the one `package.json` resolved to). This was the inverse of how `@mariozechner/pi-coding-agent` ships, where `dist/` mirrors `src/` per-file, every module has a sibling `.d.ts` with full JSDoc, and the docs/examples are shipped in the tarball — so an AI agent reading `node_modules/...` sees the exact installed version's source.
  - **New `tsconfig.lib.json`** at repo root drives a per-file `tsc` compile rooted at the repo root with `outDir: ./lib/dist`. The output mirrors the source tree (`lib/dist/lib/`, `lib/dist/services/connectors/`, `lib/dist/services/traces/`, `lib/dist/services/agent/`, `lib/dist/types/`) with `declaration: true`, `declarationMap: true`, `sourceMap: true`, and `removeComments: false` so every emitted `.js` and `.d.ts` keeps its JSDoc and points back at the source via sourcemaps. `cli/` and `server/` continue to use `esbuild --bundle` because they're executed as a single entry — only the public SDK switches to per-file compile.
  - **`@/` path aliases are rewritten by `tsc-alias`** in a follow-up step (`tsc -p tsconfig.lib.json && tsc-alias -p tsconfig.lib.json --resolve-full-paths`). `tsc-alias` was already a devDependency for the same purpose elsewhere; the `--resolve-full-paths` flag adds the `.js` extension required for Node ESM resolution. After the step, zero `@/...` specifiers remain in `lib/dist/`.
  - **`docs/` and `examples/` are now shipped in the tarball** via `package.json` `files`. A new `examples/` directory at the repo root holds runnable, hand-written templates: `examples/eval-files/{demo,sdk-hooks-demo}.eval.js` (copied from `evals/` so they version with releases, not with `main`), `examples/connectors/echo-connector.ts` (smallest realistic `BaseConnector` subclass with annotated `buildPayload` / `execute` / `parseResponse`), `examples/config/agent-health.config.example.ts` (annotated `defineConfig` template), and an `examples/README.md` that points users at the in-tarball compiled source for cross-reference.
  - **`package.json` `main` / `types` / `exports`** updated to `./lib/dist/lib/index.js` / `./lib/dist/lib/index.d.ts` (the new per-file output path). The double-`lib/lib` segment is a deliberate consequence of `rootDir: "."` — it keeps the source-mirror invariant (`lib/dist/<source-path>`) without renaming anything. The published export shape (18 named exports — `defineConfig`, `BaseConnector` + 5 connector classes, `connectorRegistry`, `registerConnector`, `fetchTraces`, `expect`, `test`, `describe`, `beforeAll`, `afterAll`, `beforeEach`, `afterEach`, `judge`) is identical to before; only the on-disk layout under `lib/dist/` changed. The legacy bundling path is preserved as `build:lib:legacy` for emergency rollback.
  - **Verification**: a fresh project that does `npm install` of the produced tarball can `import { ... } from '@opensearch-project/agent-health'` and see all 18 exports load, plus navigate `node_modules/@opensearch-project/agent-health/lib/dist/services/connectors/base/BaseConnector.{js,d.ts}` and read the full base-class definition with JSDoc — exactly the same shape pi delivers. The tarball is 1.1 MB packed / 4.6 MB unpacked (415 files), up from the previous bundled output but with full debuggability for consumers and AI assistants. `npm run build:all` passes. `tests/unit/lib/` and `tests/unit/services/connectors` (the affected test trees, 821 tests) remain green. Pre-existing `React.act` failures in `tests/unit/hooks/usePersistedSet.test.ts` (9 tests) reproduce on stock `origin/main` and are unrelated.

### Fixed
- **CLI `benchmark -f file.eval.js` no longer minted fresh `TestCase` IDs on every run, growing `benchmark.testCaseIds` unbounded** ([server/routes/storage/testCases.ts](server/routes/storage/testCases.ts), [cli/commands/benchmark.ts](cli/commands/benchmark.ts), [cli/utils/apiClient.ts](cli/utils/apiClient.ts), [tests/integration/server/routes/storage/testCasesBulkUpsert.integration.test.ts](tests/integration/server/routes/storage/testCasesBulkUpsert.integration.test.ts) (new)): the CLI's legacy single-file mode posted to `POST /api/storage/test-cases/bulk` on every invocation, but the bulk endpoint always called `storage.testCases.bulkCreate(...)` regardless of whether the test cases carried provenance fields. SDK / code-imported test cases ship with `sourceFile` and `sourceHash` (set by `loadTestCasesFromModule` in `lib/testCases/loader.ts`), but the endpoint ignored them, so re-running the same .eval.js minted fresh `tc-<timestamp>-<random>` IDs every time. Combined with the CLI's set-union merge into the existing benchmark — `Set([...existing.testCaseIds, ...freshly-created])` — this made `benchmark.testCaseIds` grow by N per run for an N-test file. After three runs of a 4-test SDK file the bench held 11 test case IDs (3 + 4 + 4) even though the file's content was identical, so the run inspector showed "old" and "new" copies of the same logical test side-by-side. Three surgical changes, all backward-compatible: **(1)** the bulk endpoint now branches by provenance with a hard contract — if every incoming test case has a non-empty `sourceFile`, dispatch to `storage.testCases.bulkUpsert(...)` (matches by `(name, sourceFile)`, bumps version on `sourceHash` drift, reuses existing TestCase IDs); if none have it, dispatch to `bulkCreate` (strict-create semantics for JSON imports / UI uploads, response shape unchanged); **mixed batches are rejected with HTTP 400** because routing them through `bulkUpsert` would let a JSON item match an existing SDK record by `name` alone (the adapter's match key collapses to name-only when `sourceFile` is missing) and clobber its `sourceHash` with `undefined` — PR #254 review feedback (Copilot). The CLI never sends mixed batches anyway (each `-f` import is homogeneous), so this is a hard contract guard, not a UX paper-cut. The response shape is a superset for the upsert path: `updated` and `unchanged` appear only when the upsert branch runs. **(2)** `cli/commands/benchmark.ts` self-heals already-bloated benchmarks on the next run — before merging fresh canonical IDs into the existing benchmark's `testCaseIds`, it fetches each existing ID and drops any whose stored `(name, sourceFile)` collides with a canonical ID we just upserted but isn't the canonical ID itself; a gray `Self-healed: pruned N stale TestCase ID(s) from "<sourceFile>" left over from pre-fix runs.` line surfaces the count. The fetch outcome is now a discriminated `{ kind: 'found' | 'missing' | 'error' }` instead of a flat `null` — transient fetch failures (network blip, 5xx, timeout) are surfaced as a yellow warning and the ID is **kept** to avoid silently corrupting `benchmark.testCaseIds`; only confirmed 404s (`api.getTestCase` returned `null`) drop the ID as a dangling reference — PR #254 review feedback (Copilot). **(3)** The CLI also surfaces the upsert summary (`Imported: N created, N updated, N unchanged`) when the server returned the upsert shape; JSON imports keep the legacy `Imported N test cases` line via a `typeof bulkResult.updated === 'number'` narrow on the `BulkCreateTestCasesResponse` type (which gained `updated?` / `unchanged?` as optional fields). **Tests**: 11 new integration tests in `tests/integration/server/routes/storage/testCasesBulkUpsert.integration.test.ts` pin the contract end-to-end against the live HTTP API: SDK upsert path returns stable IDs across re-imports (`unchanged: 1`, same id), bumps version on hash drift (`updated: 1`, same id, `currentVersion > 1`), separates by `sourceFile` (same name in two files = two TestCases), the JSON path keeps its `{created, errors, testCases}` response shape with no `updated` / `unchanged` keys (backward-compat lock so existing callers that destructure `{ created, errors }` aren't surprised), repeated JSON imports stay create-only (legacy preserved), mixed batches are rejected with 400 and a precise error message (`Mixed batch rejected: ... received N with sourceFile and M without`), homogeneous SDK batches still hit upsert, a **cross-name collision regression** locks the original Copilot concern — a JSON item named like an existing SDK record cannot reach `bulkUpsert` and the SDK record's `sourceHash` and `initialPrompt` are preserved — and `ApiClient.bulkCreateTestCases` typed shape carries the new fields so the CLI's `typeof bulkResult.updated === 'number'` narrow compiles. Verified end-to-end against a real bloated benchmark on the production OpenSearch cluster — re-running the SDK file pruned 7 stale IDs and converged the bench from 11 → 4 test cases on the first post-fix run.

- **Inspect page tabs no longer render a phantom gap above the active panel's content** ([components/RunDetailsContent.tsx](components/RunDetailsContent.tsx), [components/MatcherResultsPanel.tsx](components/MatcherResultsPanel.tsx)): on the run inspector page (`/evaluations/benchmarks/:bm/runs/:run/inspect`) the LLM Judge tab and Annotations tab opened with ~50–430px of empty space above their first piece of content. Root cause: the Traces (`logs`) `TabsContent` declared an unconditional `flex flex-col min-h-0 flex-1` className. Radix tabs hides inactive panels via the `[hidden]` HTML attribute (which the user-agent stylesheet maps to `display: none`), but the user-defined `flex` class has the same CSS specificity and wins on source order — so the inactive Traces panel kept laying itself out as a flex container with non-zero height directly above the active panel. The phantom height varied with whether the trace fixture had data, which is why the gap above the LLM Judge tab was small (~48px) but the gap above the Annotations tab was huge (~430px). Fixed by gating the flex layout classes on `data-[state=active]:` so radix's hidden behaviour wins for inactive panels.
  Also, while in the same area: the Annotations tab no longer renders a redundant `Annotations` H3 inside the panel (the tab itself is already labelled `Annotations`), and the matcher detail accordion in the LLM Judge tab now exposes the full `description` (it was only available truncated in the row header) and the judge `model` field alongside the existing `expected`/`actual`/`reasoning`/`error` fields. This makes verifying matcher behaviour from a saved run actually possible without poking at storage JSON.

### Changed
- **Unified judge surface — `matcherResults[]` is now the canonical home for LLM judge verdicts** ([lib/matchers/judgeAccessor.ts](lib/matchers/judgeAccessor.ts) (new), [services/evaluation/index.ts](services/evaluation/index.ts), [services/evaluationRunner.ts](services/evaluationRunner.ts), [services/benchmarkRunner.ts](services/benchmarkRunner.ts), [services/traces/browserRecovery.ts](services/traces/browserRecovery.ts), [services/storage/asyncRunStorage.ts](services/storage/asyncRunStorage.ts), [components/RunDetailsContent.tsx](components/RunDetailsContent.tsx), [components/QuickRunModal.tsx](components/QuickRunModal.tsx), [components/TrajectoryCompareView.tsx](components/TrajectoryCompareView.tsx), [services/skills/grader.ts](services/skills/grader.ts), [services/report/html/htmlTemplate.ts](services/report/html/htmlTemplate.ts), [types/index.ts](types/index.ts)): the legacy `report.llmJudgeReasoning` flat string and the SDK's `report.matcherResults[*]` with `method: 'llm-judge'` were two parallel surfaces for the same conceptual data — “the LLM judge's verdict + reasoning for one invocation” — written by different code paths (the auto-judge in `services/evaluation` + 4 runner call sites for the legacy field; the SDK `judge(result, claim)` matcher for the new array). Storing the same data in two places is what made [#230](https://github.com/opensearch-project/agent-health/issues/230) possible (the trace-mode placeholder `Waiting for traces to become available…` survived in the legacy field for deterministic SDK runs and bled through to the UI). The two surfaces are now collapsed onto **`matcherResults[]`** as the single source of truth via two new helpers in `lib/matchers/judgeAccessor.ts`: `buildJudgeMatcherEntry(judgment, { claim, model })` (pure converter from `JudgeResult` → `MatcherResult`), `recordJudgeMatcherResult(report, judgment, opts)` (mutates the report and keeps the legacy field as a derived shim), `getJudgeMatcherResults(report)` (read-side accessor that returns existing `[llm-judge]` entries OR synthesizes one from the legacy field for old reports, treating the trace-mode placeholder as “no judge ran”), and `getJudgeReasoningText(report)` (flat-string convenience for surfaces that historically read `llmJudgeReasoning`). All five legacy-judge writers — `services/evaluation/index.ts` (2 returns), `services/evaluationRunner.ts:waitForTracesAndJudge`, `services/benchmarkRunner.ts` (2 trace-mode update paths), `services/traces/browserRecovery.ts` — now push a `[llm-judge]` entry into `matcherResults` alongside writing the legacy field. All readers — the run-details inspector, QuickRunModal, TrajectoryCompareView, the skills grader, and the exported HTML report — now consume `getJudgeReasoningText` / `getJudgeMatcherResults` instead of `report.llmJudgeReasoning` directly. The standalone “Judge Reasoning” card was removed from `RunDetailsContent` because judge entries now flow through the existing `MatcherResultsPanel` as `[llm-judge]` rows with full reasoning, score, and durationMs — same UI component, single panel, no duplication. **Storage**: zero impact — both fields were already declared in the index mapping (`server/constants/indexMappings.ts`), no reindex needed; the `asyncRunStorage.updateReport` allow-list was extended to propagate `matcherResults` on partial updates. **Backward compat (Option B)**: `EvaluationReport.llmJudgeReasoning` is marked `@deprecated` but still populated by writers as a derived convenience shim (carries the most recent judge reasoning so external scripts that read it directly continue to work; SDK multi-judge runs deliberately leave it `''` to signal that consumers must look at `matcherResults`). Old reports persisted before this change render identically via the read-time synthesis path. **Tests**: 23 unit tests for the new accessor in [tests/unit/lib/matchers/judgeAccessor.test.ts](tests/unit/lib/matchers/judgeAccessor.test.ts) cover the four behaviour states (matcher-only / legacy-only / both / placeholder), the placeholder-as-no-judge convention (issue #230 regression lock), the multi-judge join in `getJudgeReasoningText`, the round-trip property (`recordJudgeMatcherResult` then `getJudgeMatcherResults` sees the same entry), the BC shim (legacy field still populated after a write), and the `expectedOutcomes` formatter handling both `string[]` and the legacy `{ rootCauses, requiredFacts, conclusions }` object shape that ships on persisted test cases. All 805 affected unit tests across `tests/unit/lib/matchers/`, `tests/unit/services/{evaluationRunner*,benchmarkRunner.test.ts}`, `tests/unit/services/traces/`, `tests/unit/services/{evaluation,skills,storage}/` continue to pass.
- **UI labels: "LLM Judge Reasoning" → "Judge Reasoning", "Conversation History" → "Test Case Output"** ([components/RunDetailsContent.tsx](components/RunDetailsContent.tsx), [components/evals3/TestCaseDetailPage.tsx](components/evals3/TestCaseDetailPage.tsx), [components/QuickRunModal.tsx](components/QuickRunModal.tsx), [components/TrajectoryCompareView.tsx](components/TrajectoryCompareView.tsx), [components/comparison/sections/JudgeSection.tsx](components/comparison/sections/JudgeSection.tsx), [components/TrajectoryView.tsx](components/TrajectoryView.tsx), [services/report/html/htmlTemplate.ts](services/report/html/htmlTemplate.ts)): the run-report inspector and live-run panel previously labelled the reasoning section "LLM Judge Reasoning", which is misleading now that non-LLM (deterministic / SDK matcher) evaluations also surface their explanation through the same field — and the streaming trajectory tab was labelled "Conversation History" even though it shows tool calls and tool results, not just a chat transcript. Tab and section headers across `RunDetailsContent`, the `LiveRunPanel` in `TestCaseDetailPage`, `QuickRunModal`, `TrajectoryCompareView`, `JudgeSection`, the empty-state in `TrajectoryView`, and the exported HTML report now read **Judge Reasoning** and **Test Case Output**. Affected unit tests (`htmlTemplate.test.ts`, `HtmlFormatter.test.ts`) and the e2e spec `tests/e2e/test-case-detail-live-run.spec.ts` were updated to match the new strings. Part of [#242](https://github.com/opensearch-project/agent-health/issues/242).

### Fixed
- **SDK `traces` fixture now reflects real OTel data** ([lib/matchers/traces.ts](lib/matchers/traces.ts), [services/traces/fetchSpansForRun.ts](services/traces/fetchSpansForRun.ts), [services/evaluationRunner.ts](services/evaluationRunner.ts), [services/benchmarkRunner.ts](services/benchmarkRunner.ts), [docs/SDK.md](docs/SDK.md)): in 0.5.x the code-based SDK's `traces` fixture was hard-coded to `emptyTracesAccessor()` regardless of the agent's `useTraces` setting, so every accessor returned `0` / `[]`. Trace-based assertions like `expect(traces.totalTokens).to.be.lessThan(10_000)` therefore passed silently against `0` even when the agent actually used 12 000 tokens — a green matcher that measured nothing ([#230](https://github.com/opensearch-project/agent-health/issues/230)). The runner now constructs the fixture three ways: (a) `useTraces: false` agents keep the silent-zeros opt-out path; (b) `useTraces: true` runs poll the existing `fetchTracesByRunIds` endpoint via a new lightweight `fetchSpansForRun` helper (default 10 × 1 s for SDK interactivity, configurable via the agent's `tracePolling` block or the `TRACE_POLL_INTERVAL_MS` / `TRACE_POLL_MAX_ATTEMPTS` env vars; hard-capped at 60 attempts) and feed the spans through the already-implemented `buildTracesAccessor` so token / cost / span-duration aggregates are real; (c) `useTraces: true` runs that produce no `runId`, hit a fetch error, or simply find no spans return a loud-failure accessor whose every getter throws with a specific reason — `agent has useTraces=true but produced no runId for trace correlation`, `fetch failed for runId=…: <underlying error>`, or `no spans found for runId=… after polling — verify the agent's OTel exporter is reachable`. Coverage: 15 unit tests for the three accessors (incl. a dedicated `regression #230` case), 11 unit tests for the polling helper (first-attempt success, retry until spans appear, persistent-error surfacing, transient-then-clean clearing, cap enforcement, invalid-input handling, configured interval), and 6 runner-level tests covering the full A–F matrix from the verification plan (opt-out, no spans, the original bug — 12 k tokens fails `lessThan(10_000)`, 5 k tokens passes, missing runId, persistent fetch error surfaced verbatim). End-to-end SDK demos under [evals/issue-230-*.eval.js](evals/) exercise the same paths through the live HTTP API against a real OTel-instrumented agent: `issue-230-verification.eval.js` (loud-failure mode against an agent whose exporter isn't reachable), `issue-230-judge-verify.eval.js` (opt-out path + LLM judge wiring on the demo agent), and `issue-230-pipeline-e2e.eval.js` (full pipeline — fetch + fixture + judge — all-green when OTel data is healthy).

- **Trace correlation conventions for unified test_case ↔ agent trace trees** ([services/connectors/types.ts](services/connectors/types.ts), [services/connectors/base/BaseConnector.ts](services/connectors/base/BaseConnector.ts), [services/connectors/subprocess/SubprocessConnector.ts](services/connectors/subprocess/SubprocessConnector.ts), all concrete connectors, [services/benchmarkRunner.ts](services/benchmarkRunner.ts), [server/services/tracesService.ts](server/services/tracesService.ts), [components/RunDetailsContent.tsx](components/RunDetailsContent.tsx), [AGENTS.md](AGENTS.md)): when agent-health ran a Claude Code (or any other) test case, the `test_case` eval span and the agent's own spans landed in OpenSearch as **two unrelated trace trees** with different `traceId`s — querying by `runId` would only return the eval span, leaving 50+ agent spans (e.g. `claude_code.interaction`, `claude_code.llm_request`, `claude_code.tool.execution`) invisible from the run-report Traces tab. Per-agent eyeballing of an agent's spans required hand-crafted OpenSearch queries on `service.name` + time window, which any teammate sharing the cluster would foul. Three layered correlation strategies, applied in priority order:
  - **Strategy A (W3C trace context, single trace tree).** The `test_case` span is now started **before** the connector invokes the agent (was: started after, with `agentRunId` baked into the start attributes), and `connector.execute` is wrapped in `context.with(caseSpanContext, …)` so the eval span is the active OTel context when the connector runs. New `BaseConnector.buildTraceparentEnv()` and `BaseConnector.injectTraceparentHeaders()` helpers read the active span and emit a W3C `TRACEPARENT=00-<traceId>-<spanId>-01` value. Subprocess connectors (`SubprocessConnector`, `claude-code`, `kiro`, `pi`) inject it as an env var; HTTP connectors (`agui-streaming`, `rest`, `openai-compatible`, `langgraph`) inject it as a `traceparent` header. Any agent whose OTel SDK respects W3C (which includes upstream Claude Code, all `@opentelemetry/sdk-*`-using agents) adopts the eval span as parent context, so the agent's root span (e.g. `claude_code.interaction`) becomes a child of `test_case` and shares the same `traceId`. Verified end-to-end: pointing the upstream Claude Code binary at a local OTLP sink with this setup produced 1 root + 11 LLM + 19+19+19 tool spans on a single trace.
  - **Strategy B (`gen_ai.request.id` attribute, loose link).** Existing convention preserved: `SubprocessConnector` continues to export `AGENT_EVAL_RUN_ID=<runId>` so agents we instrument can tag spans with `gen_ai.request.id == runId`, and the eval span itself already carries the same attribute. The OpenSearch query unions A and B via `bool.should` so spans matching either are returned without duplication.
  - **Strategy C (`service.name` + time-window fallback, always-on).** Each connector declares a `traceContext.serviceName` default (`claude-code-agent`, `kiro-agent`, `pi-agent`, `observio-sample-agent`); the run-report Traces tab always expands the query with `serviceName == <agent's> AND startTime IN [run.startedAt − slack, run.endedAt + slack]` and unions it with A/B via `bool.should`. Originally landed as opt-in via an "Include all agent spans in window" checkbox — was promoted to always-on after a verification pass showed the run-report Traces tab landed on a near-empty trace tree by default (just the eval `test_case` span) until users noticed the toggle, which was a worse cost than the noise risk it guards against. The window slack is 30 minutes for older runs without `performanceMetrics.durationMs` set, and `durationMs + 60s` otherwise. Service-name resolution prefers the agent's `traceServiceName` override if declared in `agent-health.config.ts`, then a built-in protocol→name convention map, then a `<agentKey>-agent` fallback.
  - **`/api/traces` extended.** New `agents: [{serviceName, startedAt, endedAt}]` field on `TraceQueryParams` / `TracesQueryOptions` (validated server-side); when 2+ correlation clauses are present the query builder switches from `bool.must` to `bool.should + minimum_should_match: 1` so spans matching *any* strategy are unioned. New `services/traces/index.ts → fetchTracesForRun({runId, evalTraceId?, includeWindowFallback?, windowAgents?})` is the one-call helper the run-report uses.
  - **`runSingleUseCase` (the standalone-run path the UI's *Run* button uses)** got the same `startTestCaseSpan` → `context.with(…)` → `setAttribute(ATTR_AGENT_HEALTH_AGENT_RUN_ID, runId)` → `finalizeTestCaseSpan(…)` rewiring as the benchmark loop. The pre-existing `emitDeferredTestCaseSpan(…, agentTraceId)` post-hoc trace-stitching path (used by trace-mode polling completions) is left in place as a fallback for late-arriving judge results.
  - **Per-agent override.** Users can override defaults per-agent in `agent-health.config.ts` via `connectorConfig.traceContext: { propagateEnv?, propagateHeader?, serviceName? }` — useful for managed/3rd-party agents that emit under custom `service.name`s.
  - **Tests.** New `tests/unit/services/connectors/base/BaseConnector.test.ts` cases for `buildTraceparentEnv()` and `injectTraceparentHeaders()` register a real `AsyncLocalStorageContextManager` + `W3CTraceContextPropagator` so the helpers see actual context flow (no-op global API alone can't propagate through `context.with`). Existing `ClaudeCodeConnector` tests for `tool_result` were updated to use the real Claude Code wire format — `type:'user'` messages with `tool_result` content blocks — since the previous fixture encoded an older buggy assumption (top-level `type:'tool_result'`) that the connector was matching but Claude Code never actually emits.
- **Documentation.** AGENTS.md gets a new "Trace correlation conventions" section explaining all three strategies, the per-agent override pattern, and the per-connector `serviceName` defaults table.

### Fixed
- **AI Assistant chat: incorrect answers and stuck flows**: The `/assistant` chat would speculate instead of answering grounded questions, and frequently halt after the first or second turn. Several issues fixed together:
  - **Stream-json parser**: rewrote the NDJSON parser to walk the real claude CLI shape (`parsed.message.content[].text`) instead of the never-emitted `parsed.subtype === 'text'` form, which previously yielded zero deltas and surfaced a confusing "stream completed without returning a full response" error to assistant-ui.
  - **Grounded run/benchmark/test-case context**: server now eagerly fetches the active run, benchmark, and test case from storage and inlines a JSON snapshot (status, accuracy, judge reasoning, improvement strategies, last 30 trajectory steps, expected outcomes) into the system prompt. The assistant can answer "why did this run fail?" without making a tool call.
  - **Real session continuity via `--resume`**: each session now gets a stable UUID; the first turn passes `--session-id <uuid>` and follow-ups pass `--resume <uuid>` so claude keeps its own conversation state. Stops the per-turn re-init cost (~42k cached tokens previously paid every turn) and removes quadratic prompt growth.
  - **Stripped CLAUDECODE / CLAUDE_CODE_* env vars from the spawned child**: when the server is started from inside an active Claude Code session, the nested CLI inherited `CLAUDECODE=1` and refused to run cleanly.
  - **Empty-response handling**: when the CLI exits 0 with no text (e.g. a tool-call-only turn or a fully denied permission gate), the route now emits a clear `error` SSE event with stderr context and a denial count instead of a blank assistant bubble.
  - **`permission_denials` surfaced in the chat**: when the `result` event carries denials, the response now ends with a brief note listing the denied tool names so the user can pre-approve them.
  - **SSE keepalive**: the `/api/assistant/chat` route now sends a comment ping every 15 s so dev tunnels and proxies don't drop the connection during long claude turns.
  - **Configurable timeout**: `ASSISTANT_TIMEOUT_MS` env var (default 600 s) replaces the hard-coded 180 s ceiling.
  - **Fallback history cap**: Bedrock and LiteLLM fallbacks now trim the in-memory message log to the last 20 turns before sending.
  - **Discoverable assistant trigger + page-aware suggestions**: replaced the unobtrusive `?` button with a sparkle (✨) gradient trigger that pulses once on first paint and animates on hover, so the AI assistant reads as a productive feature instead of a help-docs link. On routes with a clear "moment" (a run detail page, a benchmark, the traces page, the dashboard, a test case), a one-time tooltip nudge floats above the trigger ("Want me to explain this run?", "Spot the slow span?", etc.) and is sessionStorage-deduped so it doesn't repeat in the same browser session. The empty-state suggestions inside the modal are now derived from the current URL — e.g. on a run page you see "Why did this run fail or succeed?" / "How do I apply the improvement strategies?" / "What was the agent supposed to do here?" instead of three generic prompts that didn't reflect what the assistant can actually answer with the grounded context now wired in.
  - **Assistant cannot strand the UI on a tool-use block**: the chat surface has no tool execution backend (no Skill, Bash, MCP, etc.) but the spawned `claude` CLI would sometimes emit a `tool_use` content block as its next step (e.g. "Let me find the SOP that drives /my-agent…" → invoke `Skill`). Without a tool runtime, the turn ended with a streaming cursor and the user saw no closing thought. Three fixes applied: (1) `--disallowed-tools '*'` now passed to the spawn so the CLI refuses tool calls outright, (2) the system prompt explicitly tells the model "no tools enabled — do not say 'Let me check…'", (3) any `tool_use` block that does slip through is rendered as an inline note ("Tried to invoke `Skill` here — tool execution is disabled in this chat") instead of a silent end.
- **Config startup log accuracy**: When `agent-health.config.json` is the only config on disk (no code-as-config `.ts/.js/.mjs` variant), the loader previously logged the misleading `"No config file found, using defaults + environment variables"` — even though server services (`configService`, `customAgentStore`, `dataSourceConfig`, `remoteConfig`) were in fact reading the JSON file and driving OpenSearch / Bedrock / agent endpoints.
