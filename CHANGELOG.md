### Added

### Fixed
- **Storage/observability OpenSearch clients: SigV4 credentials now self-heal within minutes of a rotation instead of wedging until a restart** ([server/services/opensearchClientFactory.ts](server/services/opensearchClientFactory.ts), [server/services/storageInitializer.ts](server/services/storageInitializer.ts), [server/adapters/index.ts](server/adapters/index.ts), [server/adapters/opensearch/StorageModule.ts](server/adapters/opensearch/StorageModule.ts)): a long-running server's SigV4-signed OpenSearch client would wedge after the resolved AWS credentials rotated (e.g. hourly `ada credentials update`) — every storage/traces op started failing with opensearch-js's opaque, bodiless `Response Error` (a 403 under the hood) while the cluster was green and a fresh CLI call worked; only a process restart recovered. Root cause: `getCredentials()` itself re-resolved fresh credentials on every call, but opensearch-js's own transport only re-invokes `getCredentials()` once it decides the **currently cached** credentials object is expired — and session/profile credentials resolved from `~/.aws/credentials` (as `ada` writes them) carry **no** `expiration`/`needsRefresh()`/`expired` field, so that check never fires again after the very first request, freezing the signer on the first-ever-resolved key for the life of the process. `resolveSigv4Credentials()` now attaches a synthetic 5-minute `expiration` whenever the provider doesn't supply one (real STS temporary-credential `expiration` values, when present, are left untouched and drive the real refresh cadence instead), which makes opensearch-js's own expiry check periodically force a re-resolve — picking up whatever `ada` last wrote to disk. This bounds the outage from "until someone notices and restarts" to "self-heals within ~5 minutes of the rotation" rather than claiming zero-downtime credential rotation. Storage/observability error surfacing (`describeOpenSearchError()`) now appends the HTTP status code (e.g. `Response Error (HTTP 403)`) at the storage-init, health-check, and test-connection call sites so an auth failure is distinguishable from a cluster-side 5xx in logs. Unit: [tests/unit/server/services/opensearchClientFactory.test.ts](tests/unit/server/services/opensearchClientFactory.test.ts) (refreshing-provider wiring, synthetic-vs-real expiration, red→green expired-then-refreshed-after-rotation simulation, status-code formatting), [tests/unit/server/services/opensearchClientFactory.sigv4Refresh.contract.test.ts](tests/unit/server/services/opensearchClientFactory.sigv4Refresh.contract.test.ts) (contract test against the REAL, unmocked opensearch-js `AwsSigv4Signer` transport: documents that expiration-less credentials never get re-resolved, then proves our synthetic expiration makes that same real transport re-invoke `getCredentials()` and pick up a rotated key), [tests/unit/server/services/storageInitializer.test.ts](tests/unit/server/services/storageInitializer.test.ts), [tests/unit/server/adapters/index.test.ts](tests/unit/server/adapters/index.test.ts), [tests/unit/server/adapters/opensearch/StorageModule.test.ts](tests/unit/server/adapters/opensearch/StorageModule.test.ts).
- **Trace-mode judging works headless for agents whose spans carry no runId — and trace polling can no longer clobber an already-judged verdict** ([services/traces/tracePoller.ts](services/traces/tracePoller.ts), [services/traces/browserRecovery.ts](services/traces/browserRecovery.ts), [services/benchmarkRunner.ts](services/benchmarkRunner.ts), [services/evaluationRunner.ts](services/evaluationRunner.ts), [server/services/traceRecoveryOnBoot.ts](server/services/traceRecoveryOnBoot.ts), [components/evals3/RunInspectorPage.tsx](components/evals3/RunInspectorPage.tsx)): the server-side trace poller correlated by **runId only** (Strategy B), but Claude Code spans carry only `session.id`, and pi/REST agents tag neither — so every `useTraces: true` run timed out after 10 minutes and errored all reports. The poller now unions Strategy B with the sessionId/service-window hints (`buildJudgeAgentsHints`) derived from the report, the `runId` requirement is dropped at every poll call site (REST-connector reports never get one), and the `MAX_POLL_CEILING` that silently clamped per-agent `tracePolling.maxAttempts` overrides back to 60 was raised to 240. Three clobber guards were added: the poller stops (without patching) when a report reaches a terminal `metricsStatus` through another path, timeout/error patches are skipped for already-judged reports, and the run-inspector's recovery fan-out now waits a 3-minute grace period so transiently-pending eager-path placeholders aren't dragged into polling that races their judge (this clobbered a live benchmark's early verdicts). The poller stamps a `calculating` claim before judging, resolves (via a new `onStopped` callback) instead of hanging `waitForTracesAndJudge` when a report was settled elsewhere, skips fetches when no correlation key is available, and post-filters window-fallback results to the report's exact `session.id` or eval-span `traceId` (stamped on the report at case start; REST and pi agents adopt the propagated traceparent) so concurrent same-service runs can't contaminate each other's judged trajectory. Boot recovery no longer tombstones **young** pending reports (`TRACE_RECOVERY_MIN_AGE_MS`, default 15 min — they are likely in-flight, possibly on a sibling server sharing the storage cluster) and resumes no-runId reports via the new hint-based polling instead of erroring them. Unit: [tests/unit/services/traces/tracePoller.test.ts](tests/unit/services/traces/tracePoller.test.ts), [tests/unit/services/traces/browserRecovery.test.ts](tests/unit/services/traces/browserRecovery.test.ts), [tests/unit/server/services/traceRecoveryOnBoot.test.ts](tests/unit/server/services/traceRecoveryOnBoot.test.ts).
- **Storage: `EvaluationRun.results` no longer blows up the `evals_experiments` index's field-count mapping** ([server/constants/indexMappings.ts](server/constants/indexMappings.ts)): a real 2026-08-26 incident crashed a 400-test-case run mid-way (243/400) with `Limit of total fields [5000] has been exceeded`. `EvaluationRun` (`docType: 'evaluation-run'`) is a top-level doc in the same index as `Benchmark` (see `OpenSearchEvaluationRunOperations`), with its own `results: Record<testCaseId, {...}>` map — distinct from the legacy nested `runs.results`, which already had this protection since 2026-03. Without an explicit mapping, OpenSearch dynamically mapped `results.<testCaseId>.*` as new fields shared across every run ever created, so a few hundred-test-case run (or enough smaller runs over time) exhausts the index's field budget. The top-level `results` field is now `{ type: 'object', enabled: false }` — same pattern as the already-protected nested field — so it's stored/read via `_source` as before (including the painless `updateResult()` partial-update path) but never parsed into the mapping; nothing queries `results.*` subfields directly. Existing installs (including the shared cluster, whose `results` field is already dynamically mapped with real sub-properties from before this fix) reject the mapping change with a `mapper_exception` on `ensureIndexes()`'s best-effort `putMapping` call — caught, surfaced as a warning, no crash, no data loss, no reindex required — so this protects fresh deployments and any not-yet-poisoned existing index immediately; an already-poisoned index needs an explicit reindex (out of scope here) to shed already-mapped fields. Also fixes a related latent bug found via `codex_review` while verifying the above: `OpenSearchEvaluationRunOperations.list({ testCaseId })` (`GET /api/storage/evaluation-runs?testCaseId=...`) issued a `nested` query against `testCaseSnapshots`, which is a plain dynamically-mapped `object` array, not `nested` — every call 500'd with `query_shard_exception: nested object under path [testCaseSnapshots] is not of nested type`. Now uses a plain `term` on the array's flattened `testCaseSnapshots.id.keyword` multi-field. Unit: [tests/unit/server/constants/indexMappings.test.ts](tests/unit/server/constants/indexMappings.test.ts), [tests/unit/server/adapters/opensearch/StorageModule.test.ts](tests/unit/server/adapters/opensearch/StorageModule.test.ts). Integration (red→green against a real OpenSearch cluster): [tests/integration/services/storage/evaluationRunMappingGrowth.integration.test.ts](tests/integration/services/storage/evaluationRunMappingGrowth.integration.test.ts) (synthesizes 500 test-case results, asserts field-count via `_mapping`), [tests/integration/services/storage/evaluationRunTestCaseIdFilter.integration.test.ts](tests/integration/services/storage/evaluationRunTestCaseIdFilter.integration.test.ts) (reproduces the query_shard_exception pre-fix, filters correctly post-fix).

- **CLI `run`: trace-mode agents are no longer reported FAILED before the judge has run** ([cli/commands/run.ts](cli/commands/run.ts), [cli/utils/apiClient.ts](cli/utils/apiClient.ts)) ([#333](https://github.com/opensearch-project/agent-health/issues/333)): for a `useTraces` agent the server emits the SSE `completed` event **before** the background trace poller runs the judge (`metricsStatus: 'pending'`, no `passFailStatus`), and the CLI collapsed that not-yet-judged snapshot into `FAILED` — contradicting the persisted report, which the judge later marked `passed`. The CLI now keeps polling until the judge verdict lands (`metricsStatus` leaves `pending`), shows a "Waiting for traces / judge verdict..." spinner meanwhile, and renders a `PENDING` (not `FAILED`) status if the wait times out; `pollReportStatus` no longer treats a judge-pending report as terminal. - **Traces UI: tool span input/output is now displayed (OTel GenAI events + message attributes)** ([components/traces/SimpleSpanAttributesTable.tsx](components/traces/SimpleSpanAttributesTable.tsx), [components/traces/SpanInputOutput.tsx](components/traces/SpanInputOutput.tsx), [components/traces/SpanDetailsPanel.tsx](components/traces/SpanDetailsPanel.tsx)) ([#319](https://github.com/opensearch-project/agent-health/issues/319)): OTel GenAI conveys tool arguments/results as span **events** (`gen_ai.tool.message` / `gen_ai.choice` — what the Strands SDK emits) or as `tool_call`/`tool_call_response` parts inside `gen_ai.input.messages`/`gen_ai.output.messages`, but the trace UI only read span attributes — and checked the non-spec names `gen_ai.tool.input`/`gen_ai.tool.output` — so tool spans showed no INPUT/OUTPUT anywhere. The run-detail drawer table now folds `span.events` in as `<event>.<field>` rows, and both I/O extractors read the event convention and the structured message attributes (spec attributes `gen_ai.tool.call.arguments`/`.result` still take precedence; the non-spec names remain as last-resort vendor fallbacks). - **Trace-mode judge: verdicts no longer flip on refresh, and trace-only agents are judged from their traces** ([services/traces/tracePoller.ts](services/traces/tracePoller.ts), [services/traces/messageExtraction.ts](services/traces/messageExtraction.ts), [services/traces/browserRecovery.ts](services/traces/browserRecovery.ts), [components/RunDetailsContent.tsx](components/RunDetailsContent.tsx), [services/benchmarkRunner.ts](services/benchmarkRunner.ts), [services/evaluationRunner.ts](services/evaluationRunner.ts)) ([#320](https://github.com/opensearch-project/agent-health/issues/320)): two root causes. (1) *Judge raced itself across runtimes*: the browser "recovery" poller in `RunDetailsContent` ran its own inline judge concurrently with the server-side poller and persisted a **divergent** field set (no `matcherResults`), so which verdict the UI showed depended on write/read timing — pass on first render, fail after refresh. The component now delegates to the shared `ensureTracePollingForReport`, which writes the canonical `matcherResults` surface and **re-reads the persisted report before judging, bailing out if a verdict already landed** — the browser path is a true fallback that never overwrites a server verdict. (2) *Judge graded a tool-call-less trajectory*: without a `buildTrajectory` hook the trace poller returned an empty trajectory and the judge graded the AG-UI stream (final message only), concluding "no tool was invoked" even though the tool calls were right there in the spans. The poller now falls back to the generic `spansToTrajectory` conversion, and `messageExtraction` reads the spec/event-based tool conventions (and emits the `tool_call` step even when argument capture is off) so the judge sees what actually happened. Unit: [tests/unit/services/traces/browserRecovery.test.ts](tests/unit/services/traces/browserRecovery.test.ts) (server-verdict-wins guard, canonical matcher surface), [tests/unit/services/traces/tracePoller.test.ts](tests/unit/services/traces/tracePoller.test.ts) (default span→trajectory).
- **CLI `benchmark -f`: long runs no longer report `0/0` when the progress stream drops** ([cli/commands/benchmark.ts](cli/commands/benchmark.ts), [cli/utils/apiClient.ts](cli/utils/apiClient.ts), [cli/utils/evaluationRunOutcome.ts](cli/utils/evaluationRunOutcome.ts)): the unified evaluation-run path read the final run **once**, the moment the SSE progress stream ended. On a long run (e.g. a subprocess agent that takes ~10 min) a proxy idle-timeout drops the stream after a few minutes, so the CLI reported partial/`0/0` results — or `fetch failed` — even though the server kept executing and persisting server-side (WebIR user feedback). Now the SSE read loop tolerates a mid-stream disconnect (as long as the runId was captured) and the CLI **polls `/api/storage/evaluation-runs/:id` until the run reaches a terminal state** (`ApiClient.pollEvaluationRunStatus`, mirroring the existing `pollRunStatus` fallback) before reporting — reading the true result from storage. Default poll budget 60 min (subprocess agents can be slow). The recovered run is also no longer blindly reported as a success: a `failed`/`cancelled` terminal status now fails the command with the server's error, and a poll that times out while the run is still `pending`/`running` says so honestly instead of claiming completion; the printed `X/Y test cases` count is computed fresh from the polled run's results rather than the stale pre-disconnect SSE count. Unit: [tests/unit/cli/utils/apiClient.test.ts](tests/unit/cli/utils/apiClient.test.ts) (polls until terminal after a `running` read; returns immediately when already terminal), [tests/unit/cli/commands/benchmark.test.ts](tests/unit/cli/commands/benchmark.test.ts) (`resolveUnifiedRunOutcome`: success/failed/cancelled/timeout, fresh vs. stale count).
- **Loud mock judge: the `demo` provider no longer silently reports a "100% pass"** ([server/routes/judge.ts](server/routes/judge.ts), [types/index.ts](types/index.ts)) ([#394](https://github.com/opensearch-project/agent-health/pull/394)): the built-in `demo`/mock judge returns a semi-random pass **without calling an LLM**, but the only hint was a footnote at the *bottom* of the reasoning — so a real benchmark whose judge model resolved to `demo-model` looked like it passed when nothing was actually judged (WebIR user feedback). Now the mock verdict (1) sets a structured `warning` field on the `JudgeResponse` (a real provider never sets it), (2) leads the reasoning with a `⚠️ MOCK JUDGE — NOT A REAL EVALUATION` banner at the **top**, and (3) emits an always-on `console.warn` server-side naming the resolved model and how to pin a real judge. Integration: [tests/integration/server/routes/judge.integration.test.ts](tests/integration/server/routes/judge.integration.test.ts) (asserts the `warning` field + banner-at-top).
- **Comparison page: 431 "Request Header Fields Too Large" silently rendered every test-case cell "— Not run"** ([services/storage/asyncRunStorage.ts](services/storage/asyncRunStorage.ts), [components/comparison/ComparisonPage.tsx](components/comparison/ComparisonPage.tsx)): `ComparisonPage`'s report loader called `asyncRunStorage.getReportsByIds()`, which issued **one** unchunked `GET /api/storage/runs?ids=<all report ids comma-joined>` request. With a few runs over a large benchmark (verified in production, 2026-08-26: 4 runs x 400 test cases) that URL/query blows past the server's header/URL size limit and the request fails with `431 Request Header Fields Too Large`; the loader had no error handling, so the failure was silently treated as "no reports" and every cell rendered "Not run" even though the header scoreboard (which reads denormalized `run.stats`, not per-report fetches) rendered correctly. `getReportsByIds()` now chunks ids into batches of 100 fired in parallel (same pattern as the existing `getReportSummariesByIds()` chunking and `computeBatchMetrics()`'s `Promise.all`-over-chunks), and a genuine chunk failure now propagates to a visible error banner on the page instead of being swallowed into an empty report map. Unit: [tests/unit/services/storage/asyncRunStorage.test.ts](tests/unit/services/storage/asyncRunStorage.test.ts) (chunking, merge-across-chunks, URL-length regression guard at 1600 ids, failure propagation — all verified red against the pre-fix code); e2e: [tests/e2e/comparison-batched-reports.spec.ts](tests/e2e/comparison-batched-reports.spec.ts) (431 on an unchunked >100-id request renders real cells once chunked; a genuine chunk failure surfaces the error banner instead of a silent "Not run").

### Added

Server-side resolution is unchanged — built-in evaluator ids carry a `system-` prefix (e.g. `system-rca-default`) and resolve via `getSystemEvaluatorById`; any other id is treated as a storage id and resolved via `storage.evaluators.getById`. The SDK now sends the same shape the UI does.
  - **Run-level default** — a new `bindJudge({ evaluatorId, model })` factory in `lib/testCases/judge.ts` returns a callable with run-level defaults pre-applied, and the runner injects `bindJudge({ evaluatorId: run.evaluatorId, model: bedrockModelId })` into the **hook orchestrator's fixture factory** in both [services/evaluationRunner.ts](services/evaluationRunner.ts) and [services/benchmarkRunner.ts](services/benchmarkRunner.ts) (it lives on the orchestrator factory now that lifecycle hooks own fixture creation). Test bodies that destructure (`async ({ judge }) => ...`) automatically inherit the run's evaluator on every call — no per-call argument needed. Per-call options still win, so a single matcher in a test can override (`await judge(result, claim, { evaluatorId: 'product-gap-eval' })`). Imported `judge` (from `require('@opensearch-project/agent-health')`) stays unbound — use it when you genuinely want the server default regardless of run config.
  - **Tests** — 11 unit tests in [tests/unit/lib/testCases/judge.test.ts](tests/unit/lib/testCases/judge.test.ts) cover the new options surface (per-call `evaluatorId` lands on the body, omitted means "server default", legacy `judge(trajectory, [claims])` still works, failed verdict still throws) and the `bindJudge` precedence rules (bound default applied when no per-call value, per-call override wins, explicit per-call `undefined` falls through to the bound default rather than wiping it, `bindJudge(undefined)` / `bindJudge({})` short-circuit to the unbound function). 2 new tests in [tests/unit/services/evaluationRunner.deterministic.test.ts](tests/unit/services/evaluationRunner.deterministic.test.ts) prove the runner-level wiring end-to-end: capture the `judge` fixture handed to a deterministic test body, invoke it with a mocked `fetch`, and verify the request body carries `run.evaluatorId` automatically (and is absent when `run.evaluatorId` is undefined). A CLI subprocess integration test in [tests/integration/cli/benchmarkEvaluatorId.integration.test.ts](tests/integration/cli/benchmarkEvaluatorId.integration.test.ts) mirrors the #245-style coverage — spawns the real CLI binary with a bogus `-e definitely-does-not-exist` against a tiny SDK fixture and verifies the persisted matcherResults reflect the precedence rules end-to-end (per-call override passes, bound default fails with the exact `Evaluator not found` error from `/api/judge`).

### Fixed
- **CLI `benchmark -f file.eval.js` no longer minted fresh `TestCase` IDs on every run, growing `benchmark.testCaseIds` unbounded** ([server/routes/storage/testCases.ts](server/routes/storage/testCases.ts), [cli/commands/benchmark.ts](cli/commands/benchmark.ts), [cli/utils/apiClient.ts](cli/utils/apiClient.ts), [tests/integration/server/routes/storage/testCasesBulkUpsert.integration.test.ts](tests/integration/server/routes/storage/testCasesBulkUpsert.integration.test.ts) (new)): the CLI's legacy single-file mode posted to `POST /api/storage/test-cases/bulk` on every invocation, but the bulk endpoint always called `storage.testCases.bulkCreate(...)` regardless of whether the test cases carried provenance fields. SDK / code-imported test cases ship with `sourceFile` and `sourceHash` (set by `loadTestCasesFromModule` in `lib/testCases/loader.ts`), but the endpoint ignored them, so re-running the same .eval.js minted fresh `tc-<timestamp>-<random>` IDs every time. Combined with the CLI's set-union merge into the existing benchmark — `Set([...existing.testCaseIds, ...freshly-created])` — this made `benchmark.testCaseIds` grow by N per run for an N-test file. Three surgical changes, all backward-compatible: **(1)** the bulk endpoint now branches by provenance with a hard contract — if every incoming test case has a non-empty `sourceFile`, dispatch to `storage.testCases.bulkUpsert(...)` (matches by `(name, sourceFile)`, bumps version on `sourceHash` drift, reuses existing TestCase IDs); if none have it, dispatch to `bulkCreate` (strict-create semantics for JSON imports / UI uploads, response shape unchanged); **mixed batches are rejected with HTTP 400** because routing them through `bulkUpsert` would let a JSON item match an existing SDK record by `name` alone (the adapter's match key collapses to name-only when `sourceFile` is missing) and clobber its `sourceHash` with `undefined` — PR #254 review feedback (Copilot). The CLI never sends mixed batches anyway (each `-f` import is homogeneous), so this is a hard contract guard, not a UX paper-cut. The response shape is a superset for the upsert path: `updated` and `unchanged` appear only when the upsert branch runs. **(2)** `cli/commands/benchmark.ts` self-heals already-bloated benchmarks on the next run — before merging fresh canonical IDs into the existing benchmark's `testCaseIds`, it fetches each existing ID and drops any whose stored `(name, sourceFile)` collides with a canonical ID we just upserted but isn't the canonical ID itself; a gray `Self-healed: pruned N stale TestCase ID(s) from "<sourceFile>" left over from pre-fix runs.` line surfaces the count. The fetch outcome is now a discriminated `{ kind: 'found' | 'missing' | 'error' }` instead of a flat `null` — transient fetch failures (network blip, 5xx, timeout) are surfaced as a yellow warning and the ID is **kept** to avoid silently corrupting `benchmark.testCaseIds`; only confirmed 404s (`api.getTestCase` returned `null`) drop the ID as a dangling reference — PR #254 review feedback (Copilot). **(3)** The CLI also surfaces the upsert summary (`Imported: N created, N updated, N unchanged`) when the server returned the upsert shape; JSON imports keep the legacy `Imported N test cases` line via a `typeof bulkResult.updated === 'number'` narrow on the `BulkCreateTestCasesResponse` type (which gained `updated?` / `unchanged?` as optional fields). **Tests**: 11 new integration tests in `tests/integration/server/routes/storage/testCasesBulkUpsert.integration.test.ts` pin the contract end-to-end against the live HTTP API: SDK upsert path returns stable IDs across re-imports (`unchanged: 1`, same id), bumps version on hash drift (`updated: 1`, same id, `currentVersion > 1`), separates by `sourceFile` (same name in two files = two TestCases), the JSON path keeps its `{created, errors, testCases}` response shape with no `updated` / `unchanged` keys (backward-compat lock so existing callers that destructure `{ created, errors }` aren't surprised), repeated JSON imports stay create-only (legacy preserved), mixed batches are rejected with 400 and a precise error message (`Mixed batch rejected: ... received N with sourceFile and M without`), homogeneous SDK batches still hit upsert, a **cross-name collision regression** locks the original Copilot concern — a JSON item named like an existing SDK record cannot reach `bulkUpsert` and the SDK record's `sourceHash` and `initialPrompt` are preserved — and `ApiClient.bulkCreateTestCases` typed shape carries the new fields so the CLI's `typeof bulkResult.updated === 'number'` narrow compiles. - **SDK lifecycle hooks for per-test out-of-band provisioning** ([lib/testCases/define.ts](lib/testCases/define.ts), [lib/testCases/types.ts](lib/testCases/types.ts), [lib/testCases/loader.ts](lib/testCases/loader.ts), [services/hookOrchestrator.ts](services/hookOrchestrator.ts), [services/sourceResolver.ts](services/sourceResolver.ts), [services/evaluationRunner.ts](services/evaluationRunner.ts), [services/benchmarkRunner.ts](services/benchmarkRunner.ts), [docs/SDK.md](docs/SDK.md), [examples/eval-files/sdk-hooks-demo.eval.js](examples/eval-files/sdk-hooks-demo.eval.js)): the code SDK now supports Playwright-style `beforeAll` / `afterAll` / `beforeEach` / `afterEach` hooks (and the `test.beforeEach(...)` static-method form) for the use case a connector can't cover — *side-effecting* per-test setup with a teardown lifecycle, e.g. materializing a temp workspace on disk, seeding a DB, starting a sandbox, or writing fixture files the agent's tools open. Hooks attach to the file they're declared in or to the surrounding `describe()` block; nested describes inherit outer hooks; ordering is outer→inner for `beforeAll`/`beforeEach` and inner→outer for `afterEach`/`afterAll`. A new `HookOrchestrator` (`services/hookOrchestrator.ts`) implements the parallel-safety guarantees: `beforeAll` runs **exactly once per scope** even when the runner dispatches up to `concurrency` tests at once (promise-based once-latch — all parallel arrivals await the same promise), and `afterAll` runs **exactly once after the last test in its scope completes** (success or failure, via a remaining-tests counter). Hook errors never crash the runner; they surface as `MatcherResult` entries on the test, visible alongside assertion failures in the existing per-matcher UI panel. The fixtures shape gained two new fields — a read-only `testInfo` (`{ name, benchmarkPath, sourceFile, testCaseId }`) and a `provisioned: Readonly<Record<string, unknown>>` bag populated by `beforeEach` via a `provide(key, value)` helper. Each test gets its own provisioned bag so concurrent tests are fully isolated; `afterEach` reads the same keys for cleanup. When no hooks are registered the orchestrator short-circuits to a noop variant so existing tests pay zero overhead. Wired through the source resolver (`hooksByFile` / `testHookScopes` maps) and the storage routes that drive both the evaluation-run and benchmark-run paths. Closes [#229](https://github.com/opensearch-project/agent-health/issues/229).

- **Trace correlation conventions for unified test_case ↔ agent trace trees** ([services/connectors/types.ts](services/connectors/types.ts), [services/connectors/base/BaseConnector.ts](services/connectors/base/BaseConnector.ts), [services/connectors/subprocess/SubprocessConnector.ts](services/connectors/subprocess/SubprocessConnector.ts), all concrete connectors, [services/benchmarkRunner.ts](services/benchmarkRunner.ts), [server/services/tracesService.ts](server/services/tracesService.ts), [components/RunDetailsContent.tsx](components/RunDetailsContent.tsx), [AGENTS.md](AGENTS.md)): when agent-health ran a Claude Code (or any other) test case, the `test_case` eval span and the agent's own spans landed in OpenSearch as **two unrelated trace trees** with different `traceId`s — querying by `runId` would only return the eval span, leaving 50+ agent spans (e.g. `claude_code.interaction`, `claude_code.llm_request`, `claude_code.tool.execution`) invisible from the run-report Traces tab. Per-agent eyeballing of an agent's spans required hand-crafted OpenSearch queries on `service.name` + time window, which any teammate sharing the cluster would foul. Three layered correlation strategies, applied in priority order:
  - **Strategy A (W3C trace context, single trace tree).** The `test_case` span is now started **before** the connector invokes the agent (was: started after, with `agentRunId` baked into the start attributes), and `connector.execute` is wrapped in `context.with(caseSpanContext, …)` so the eval span is the active OTel context when the connector runs. New `BaseConnector.buildTraceparentEnv()` and `BaseConnector.injectTraceparentHeaders()` helpers read the active span and emit a W3C `TRACEPARENT=00-<traceId>-<spanId>-01` value. Subprocess connectors (`SubprocessConnector`, `claude-code`, `kiro`, `pi`) inject it as an env var; HTTP connectors (`agui-streaming`, `rest`, `openai-compatible`, `langgraph`) inject it as a `traceparent` header. Any agent whose OTel SDK respects W3C (which includes upstream Claude Code, all `@opentelemetry/sdk-*`-using agents) adopts the eval span as parent context, so the agent's root span (e.g. `claude_code.interaction`) becomes a child of `test_case` and shares the same `traceId`. Verified end-to-end: pointing the upstream Claude Code binary at a local OTLP sink with this setup produced 1 root + 11 LLM + 19+19+19 tool spans on a single trace.
  - **Strategy B (`gen_ai.request.id` attribute, loose link).** Existing convention preserved: `SubprocessConnector` continues to export `AGENT_EVAL_RUN_ID=<runId>` so agents we instrument can tag spans with `gen_ai.request.id == runId`, and the eval span itself already carries the same attribute. ### Security
- **Command injection in `SubprocessConnector`** ([services/connectors/subprocess/SubprocessConnector.ts](services/connectors/subprocess/SubprocessConnector.ts)) ([#228](https://github.com/opensearch-project/agent-health/pull/228) follow-up): the connector spawned with `shell: true` and a hand-rolled `shellQuote` that only escaped single quotes. Two new regression tests pin the contract: a malicious `'$(echo PWNED > /tmp/...)'` prompt now arrives at the child as a single literal arg, and a separate test asserts `opts.shell === false`.

### Fixed
- **`failureClusterService` cache timestamps were storing AWS retry counts, not wall-clock time** ([server/services/failureClusterService.ts](server/services/failureClusterService.ts)) ([#228](https://github.com/opensearch-project/agent-health/pull/228) follow-up): both `CacheEntry.computedAt` and `ClusterContextRecord.storedAt` were being set to `response.$metadata.attempts ?? 0` — the Bedrock SDK's per-request retry counter (typically `1`, sometimes `2-3` on transient errors). Any future cache-age / TTL logic that read the field would have been silently broken. Now both write `Date.now()`. - **Assistant `session.claudeStarted` was set on clean-exit-but-empty turns** ([server/services/assistantService.ts](server/services/assistantService.ts)) ([#228](https://github.com/opensearch-project/agent-health/pull/228) follow-up): the flag flipped to `true` immediately after the non-zero-exit check, but BEFORE the `if (!fullResponse)` empty-output check. - **Assistant dispatch could leak unhandled rejections that strand the UI** ([server/services/assistantService.ts](server/services/assistantService.ts)) ([#228](https://github.com/opensearch-project/agent-health/pull/228) follow-up): the IIFE in `streamAssistantResponse` only caught failures from `loadContextSnapshot`. ### Fixed
- **AI Assistant chat: incorrect answers and stuck flows**: The `/assistant` chat would speculate instead of answering grounded questions, and frequently halt after the first or second turn. Several issues fixed together:
  - **Stream-json parser**: rewrote the NDJSON parser to walk the real claude CLI shape (`parsed.message.content[].text`) instead of the never-emitted `parsed.subtype === 'text'` form, which previously yielded zero deltas and surfaced a confusing "stream completed without returning a full response" error to assistant-ui.
  - **Grounded run/benchmark/test-case context**: server now eagerly fetches the active run, benchmark, and test case from storage and inlines a JSON snapshot (status, accuracy, judge reasoning, improvement strategies, last 30 trajectory steps, expected outcomes) into the system prompt. The assistant can answer "why did this run fail?" without making a tool call.
  - **Real session continuity via `--resume`**: each session now gets a stable UUID; the first turn passes `--session-id <uuid>` and follow-ups pass `--resume <uuid>` so claude keeps its own conversation state. Stops the per-turn re-init cost (~42k cached tokens previously paid every turn) and removes quadratic prompt growth.
  - **Stripped CLAUDECODE / CLAUDE_CODE_* env vars from the spawned child**: when the server is started from inside an active Claude Code session, the nested CLI inherited `CLAUDECODE=1` and refused to run cleanly.
  - **Empty-response handling**: when the CLI exits 0 with no text (e.g. a tool-call-only turn or a fully denied permission gate), the route now emits a clear `error` SSE event with stderr context and a denial count instead of a blank assistant bubble.
  - **`permission_denials` surfaced in the chat**: when the `result` event carries denials, the response now ends with a brief note listing the denied tool names so the user can pre-approve them.
  - **SSE keepalive**: the `/api/assistant/chat` route now sends a comment ping every 15 s so dev tunnels and proxies don't drop the connection during long claude turns.
  - **Configurable timeout**: `ASSISTANT_TIMEOUT_MS` env var (default 600 s) replaces the hard-coded 180 s ceiling.
  - **Fallback history cap**: Bedrock and LiteLLM fallbacks now trim the in-memory message log to the last 20 turns before sending.
  - **Discoverable assistant trigger + page-aware suggestions**: replaced the unobtrusive `?` button with a sparkle (✨) gradient trigger that pulses once on first paint and animates on hover, so the AI assistant reads as a productive feature instead of a help-docs link. On routes with a clear "moment" (a run detail page, a benchmark, the traces page, the dashboard, a test case), a one-time tooltip nudge floats above the trigger ("Want me to explain this run?", "Spot the slow span?", etc.) and is sessionStorage-deduped so it doesn't repeat in the same browser session. The empty-state suggestions inside the modal are now derived from the current URL — e.g. on a run page you see "Why did this run fail or succeed?" / "How do I apply the improvement strategies?" / "What was the agent supposed to do here?" instead of three generic prompts that didn't reflect what the assistant can actually answer with the grounded context now wired in.

Without a tool runtime, the turn ended with a streaming cursor and the user saw no closing thought. Three fixes applied: (1) `--disallowed-tools '*'` now passed to the spawn so the CLI refuses tool calls outright, (2) the system prompt explicitly tells the model "no tools enabled — do not say 'Let me check…'", (3) any `tool_use` block that does slip through is rendered as an inline note ("Tried to invoke `Skill` here — tool execution is disabled in this chat") instead of a silent end.
- **Config startup log accuracy**: When `agent-health.config.json` is the only config on disk (no code-as-config `.ts/.js/.mjs` variant), the loader previously logged the misleading `"No config file found, using defaults + environment variables"` — even though server services (`configService`, `customAgentStore`, `dataSourceConfig`, `remoteConfig`) were in fact reading the JSON file and driving OpenSearch / Bedrock / agent endpoints.
